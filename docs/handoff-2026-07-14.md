## Product Summary

The application is an internal Ready Set STEM staff tool for managing the tour-to-enrollment workflow.

The core business flow is:

```text
Lead / family interest
  -> New tour scheduled
  -> Tour tracked on Home, Tours, and Pipeline
  -> Status transition recorded
  -> Tour event history retained
  -> Analytics and reporting use the same source data
```

Primary users:

- Staff: day-to-day tour and family workflow, scoped to assigned location.
- Admin: location and lead-source management, cross-location visibility.
- Super Admin: all admin capabilities plus user management.

Primary routes:

```text
/login
/home
/tours
/tours/new
/tours/:id
/tours/:id/edit
/pipeline
/analytics
/settings
/admin
/admin/users
/admin/users/new

/admin/locations
/admin/locations/new
/admin/locations/:id/edit
/admin/lead-sources
/admin/lead-sources/new
/admin/lead-sources/:id/edit
```

### Core Models

`accounts.User`

- Email-based login.
- `username = None`.
- Roles:
  - `super_admin`
  - `admin`
  - `staff`
- Optional assigned `location`.
- Case-insensitive email uniqueness constraint.
- External IDs have been added for safer references/imports.

`sites.Location`

- Location name, address, city, state, zip, phone, active flag.
- Used for role-based access and tour filtering.

`leads.LeadSource`

- Source name, description, active flag.
- Managed by admin/super admin.

`leads.Family`

- Family name, contact email, phone, notes.
- Tours are tied to families.

`tours.Tour`

- Family
- Location
- Lead source
- Assigned staff
- Child grade
- Scheduled tour date
- Current status
- External ID

Tour statuses in backend:

```text
scheduled     -> UI label: Booked
rescheduled   -> Rescheduled
toured        -> Toured
enrolled      -> Enrolled
churned       -> Churned
cancelled     -> Cancelled
no_show       -> No Show
```

`tours.TourEvent`

- Append-only event history for tour status changes and scheduling events.
- Includes status, timestamp, updated_by, notes.

`reports.CostBasis`

- Location, reporting month, cost type, amount, notes.
- Currently planned for later analytics/reporting work.

## Current Design Direction

The project has moved from an early custom blue app look toward the official Ready Set STEM visual language.

Official site inspected:

```text

```

The official site was inspected for layout, typography, color, and responsive behavior across desktop and mobile. A user-provided official-site login was used only for visual inspection. Do not store official-site credentials in the repo or handoff docs.

Observed official design patterns:

- Font families:
  - Headings: Montserrat
  - Body: Open Sans
- Main colors:
  - Deep navy: `rgb(11, 28, 65)`
  - Navy: `rgb(26, 54, 93)`
  - Gold: `rgb(251, 191, 36)`
  - White: `rgb(255, 255, 255)`
  - Soft gray-blue: `rgb(225, 231, 239)`
  - Brand blue/action blue: around `rgb(11, 115, 218)`
- Common radii:
  - Cards: `10px` to `12px`
  - Pills/buttons: `9999px`
- Common font sizing:
  - Body: `14px` to `16px`
  - Small labels: `12px` to `14px`
  - Page headings: `24px` to `30px`
  - Landing hero desktop: around `60px`
  - Landing hero mobile: around `36px`
- Mobile layout:
  - Vertical scrolling is expected.
  - Do not force every section into one viewport.
  - Cards stack vertically.
  - Avoid clipped text; wrap headings/taglines where needed.

## Design System Notes to Apply Next

Use these design principles for authenticated app pages:

- Official-brand navy text on light backgrounds.
- Brand gold as emphasis/accent, not every CTA.
- Use brand blue/action blue for primary actions, but avoid confusing it with status `Booked` if the same color is too close.
- Status colors:

```text
Booked / scheduled: official brand blue
Toured: gold/yellow
Enrolled: green
Churned: red
No Show: orange
Cancelled: gray
Rescheduled: purple
```

- Loading/no-data states should use the same style/color pattern consistently across pages.
- Cards should usually have `10px` to `12px` radius.
- Avoid large rounded decorative sections in dense staff workflows.
- Login can be expressive; post-login should be efficient and scannable.
- Font scale should not be viewport-width-only; use responsive clamps carefully.
- Prevent text clipping in buttons/cards by giving stable heights, wrapping, or reducing font sizes.
- On mobile, prefer scroll over overlap.
